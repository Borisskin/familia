# Правила проекта Familia

## Тестовая сборка Windows

Фраза пользователя «по правилам проекта сделай сборку» и равнозначная просьба о
тестовой сборке разрешают полный цикл ниже: обычные коммиты, отправку рабочих
веток, обновление постоянных веток сборки, запуск GitHub Actions, ожидание и
скачивание файлов. Эта просьба не разрешает выпуск версии.

Постоянная ветка тестовых сборок в обоих репозиториях — `build/test`:

- `Borisskin/familia`;
- `Borisskin/familia-admin`.

Каждую тестовую сборку выполнять в таком порядке:

1. Проверить состояние и изменения отдельно в корневом репозитории `familia` и
   во вложенном репозитории `admin`.
2. Все подготовленные изменения исходного кода, проверок, рабочих процессов и
   документации оформить обычными коммитами в текущих рабочих ветках. Не
   использовать `git stash create`, `git commit-tree`, отделённые снимки и
   датированные ветки сборки. Если изменений нет, пустой коммит не создавать.
3. Убедиться, что оба рабочих дерева чистые, и отправить текущие рабочие ветки в
   их `origin`.
4. В каждом репозитории обновить постоянную ветку `build/test` до только что
   отправленного коммита текущей рабочей ветки и отправить её через
   `--force-with-lease`. Перед перезаписью получить актуальное состояние
   удалённой `build/test`. Новую ветку для очередной сборки не создавать.
5. До запуска убедиться, что удалённые `build/test` указывают на ожидаемые
   коммиты обоих репозиториев.
6. Вручную запустить `.github/workflows/windows-release.yml` в
   `Borisskin/familia-admin`:

   ```powershell
   rtk gh workflow run windows-release.yml `
     -R Borisskin/familia-admin `
     --ref build/test `
     -f backend_repository=Borisskin/familia `
     -f backend_ref=build/test
   ```

7. Дождаться конечного состояния запуска. Скачивать файлы только после общего
   результата `success`. Задание `publish-draft` должно иметь результат
   `skipped`.
8. Скачать только конечные наборы `familia-admin-windows-portable`,
   `familia-admin-windows-installer` и `familia-source-pack` в каталог
   `D:\chat\familia\dist\windows-release-<версия>-github-run-<номер>\`.
9. Проверить наличие переносимой программы, установщика, архива исходников и
   всех файлов `.sha256`, затем сверить каждую контрольную сумму.
10. Сообщить номер и ссылку запуска, коммиты обоих репозиториев, локальный путь,
    список файлов и результат проверки контрольных сумм.

Для тестовой сборки запрещено:

- создавать или отправлять метки `v*`;
- выполнять `gh release create`, `gh release edit` или `gh release upload`;
- создавать черновик или выпуск GitHub Release;
- запускать публикацию вместо ручного `workflow_dispatch`;
- скачивать файлы старого запуска при ошибке текущего.

Постоянная `build/test` нужна также для повторного использования кэша Cargo.
Первый запуск этой ветки может быть холодным; следующие запуски должны обновлять
ту же ветку, а не создавать новую.
