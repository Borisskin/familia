# Архитектура

Familia — форк [nanobot](https://github.com/HKUDS/nanobot) с включенной копией [memX](https://github.com/MehulG/memX) и небольшим пакетом `familia`, который встраивает идентичность, политику и список доступа в цикл агента nanobot.

## Составные части

### `familia/` (этот репозиторий)

Тонкий слой, который превращает nanobot из агента одного пользователя в агента для нескольких участников.

```
familia/src/familia/
  identity_resolver.py   связывает входящие сообщения с principal_id
  principals.py          загружает и проверяет principals.json
  acl.py                 достижимость в family.graph + topics.graph
  policy/                движок policy.yaml (аудит + решения)
  tools/                 memory_*, send_buttons, family_graph,
                         инструменты выдачи прав из админки
  bootstrap.py           единая точка встраивания в nanobot.agent.loop
  audit.py               JSONL-журнал только на добавление + ротация 50 МБ x 5
  cli/                   CLI familia (graph_admin, audit_view)
```

### `nanobot/` (встроенный форк)

Верхнеуровневый цикл агента. Мы патчим несколько файлов, чтобы в известных точках передать управление слою `familia`: вход канала, сборка запроса, вызов инструментов, запись памяти. Патчи лежат в `patches/`.

### `memx/` (встроенная копия)

Хранилище FastAPI + Redis со списком доступа для каждого участника. У каждого
участника есть уникальный ключ API (`memx_key`); запросы проходят проверку по
`X-API-Key`. Файл доступа (`memx-config/acl.json`) связывает ключ с разрешённой
частной памятью.

Новая память физически хранится только у текущего участника. Профиль лежит в
`private:<principal>:value:user_profile`, отдельный факт — в
`private:<principal>:memory:<fact_id>`, а его адресуемое имя
`memory:<fact_id>` записывается в личный каталог
`private:<principal>:value:private_index` вместе с теми же проверенными
сервером метками. Факт и каталог изменяются одной условной операцией. Каталог
вмещает не более 256 различных имён: новое имя при заполнении получает
`catalog_full` без записи факта и без вытеснения прежних имён.

memX назначает и возвращает техническую версию `ts`; модель и клиент не
передают, не назначают и не выдумывают её. Изменение и удаление используют
только точную версию, которую ранее вернул доверенный серверный путь.
Тема остаётся меткой видимости частного факта, а не отдельным общим
хранилищем.

Семейный граф и граф тем — структурные данные, которыми управляет админка.
Сжатие чата использует того же текущего участника: итог пишется только в его
частную память и не получает метку темы.

## Поток данных: входящее сообщение

```text
1. Telegram / VK доставляет сообщение адаптеру канала.
2. nanobot вызывает familia.identity_resolver.resolve(channel, sender_id).
3. Мы ищем в principals.json -> principal_id, роль.
4. set_current_actor(principal_id) закрепляется до конца хода.
5. Цикл агента собирает запрос из общих файлов SOUL/AGENTS/TOOLS, профиля
   текущего участника, допустимой прежней `value:memory`, логических имён
   `memory:<fact_id>` из его `value:private_index` без значений атомарных
   фактов и разрешённых чужих имён, также без значений.
6. LLM создает ответ и вызовы инструментов. Сервер определяет назначение
   записи: физически это всегда частная память текущего участника; метка темы
   добавляется только после проверки существующей доступной темы.
7. Чужое атомарное имя попадает в запрос только при точной записи каталога с
   совпадающими метками, прямой семейной связи и подтверждённом общем топике.
   Профиль, служебные и секретные записи другого участника не передаются.
8. Решения политики добавляются в audit.jsonl: участник, операция, назначение,
   решение и причина.
9. Ответ уходит через тот же канал, в тот же чат. Рассылки нет.
```

При ошибке или неподтверждённом результате записи граница сжатия не
продвигается, а исходные сообщения сохраняются. Конфликт допускает безопасный
повтор после нового точечного чтения; полный каталог требует явного решения и
не приводит к потере сообщений.

## Схема хранения

Две плоскости хранения намеренно не смешиваются:

| Плоскость | Назначение | Ключ |
| --- | --- | --- |
| **Частная память memX** | профиль и отдельные факты участника | `principal_id`, `fact_id` |
| **Структурные графы** | участники, отношения, темы и их связи | админка |
| **Общие файлы** (рабочий каталог) | личность бота, описания инструментов, документы агента | единая общая правда |

Главное правило безопасности: чат пишет только в частную память говорящего.
Отношение между людьми само по себе не открывает чужую память и никогда не
разрешает запись в неё. Чтение отдельного чужого факта возможно только по
точной записи личного каталога, прямой поддерживаемой семейной связи и
проверенной сервером метке подходящей общей темы. Старые физические
`shared`/`pair`, статическое правило или отсутствие метки не заменяют ни одно
из этих условий.

## Границы доверия

```text
                    ┌────────────────────┐
                    │ Ноутбук владельца  │  (admin .exe + WebView2Loader.dll)
                    └─────────┬──────────┘
                              │ SSH (порт 22, ключ)
   ┌──────────────────────────┴──────────────────────────────────┐
   │  ВМ (Linux, root SSH only)                                  │
   │  ┌───────────────────────────────────────────────────────┐  │
   │  │ docker network: familia_default                       │  │
   │  │   familia-gateway   ──▶  memx-backend ──▶ memx-redis │  │
   │  └───────────────────────────────────────────────────────┘  │
   │  /opt/familia/{principals.json, policy.yaml, acl.json,      │
   │                .env, audit.jsonl}                           │
   └─────────────────────────────────────────────────────────────┘
                ▲                                ▲
                │                                │
   ┌────────────┴──────────┐         ┌───────────┴────────────┐
   │ Telegram channel API  │         │ LLM provider           │
   │ VK long-poll API      │         │ (OpenAI/Claude/Groq/…) │
   └───────────────────────┘         └────────────────────────┘
```

- Ноутбук владельца **доверенный**: на нем хранится SSH-ключ.
- ВМ **доверенная**: root на хосте все равно может прочитать все.
- Каналы Telegram/VK **вне границы доверия**: они видят входящие и исходящие сообщения открытым текстом.
- Поставщик LLM **вне границы доверия**: он видит только собранный для
  текущего хода контекст, который сервер уже разрешил этому участнику.

Полная модель угроз описана в [`security.md`](security.md).

## Зачем три compose-стека и почему они лежат вместе

`docker-compose.yml`, `docker-compose.memx.yml` и `docker-compose.cli.yml` разделены, чтобы каждую плоскость можно было останавливать, перезапускать, сохранять и пересобирать отдельно. На практике все три запускаются на одной ВМ и используют одну сеть Docker; админка управляет ими как единым целым.

Есть еще `docker-compose.exec-sandbox.yml` для зависимостей песочницы bubblewrap в nanobot. Он вынесен отдельно, потому что изменение настроек песочницы не должно перезапускать gateway.
